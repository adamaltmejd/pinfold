# End-to-end harness and guarantees 1 and 2

2026-11-20. First step of #297: `crates/e2e` with its harness and the
tests for rows 1 and 2. Both pass against main's binary (ef09dda) on
macOS and Linux x64. No product bug was found.

## Harness

`crates/e2e/src/lib.rs`, dependency `serde_json` only:

- `pinfold()`: `cargo build -p pinfold --locked` once per run, path taken
  from Cargo's JSON messages; on Linux the static musl release build,
  because the CLI is the guest's PID 1.
- `TestEnv`: per-test XDG config and state roots under the temp dir,
  removed on drop; `PINFOLD_*` scrubbed; commands run outside any project.
  The cache root is one per suite (`$TMPDIR/pinfold-e2e-cache`), so Linux
  fetches the pinned VMM and kernel and builds the default image once.
- `default_image()`: `localhost/pinfold/profile-default:latest`. On macOS
  an existing image in the shared store is used as it is (a rebuild would
  move a shared tag); it is built only when absent. On Linux the image
  lives in the suite cache, so it is built once per run.
- `TestEnv::up(spec)` returns a `BoxUp` after the `ready` line (read on a
  thread, ten-minute bound). Dropping it closes stdin (`down`) and reads to
  EOF; `box down NAME` only if that takes over two minutes. The owner is
  never killed first: an Apple guest would outlive it.
- `TestEnv::exec`, `BoxUp::egress_log` (the file `ready` names), and
  `Fixture`: a loopback HTTP service in the test process that records each
  request and answers a chosen status.

## Tests

Setup: macOS 27.2, Apple `container` 1.7.1, via
`CARGO_TARGET_AARCH64_APPLE_DARWIN_RUNNER="sh scripts/run-mac-e2e.sh"
cargo test -p e2e --locked`; the existing `profile-default` image was
used, none built. Linux: the persistent dev VM (Debian 13, kernel 6.12,
x64, `/dev/kvm` via the `kvm` group, no AppArmor userns restriction), a
fresh checkout in `~/pinfold-e2e-harness` with `TMPDIR` inside it,
`PATH` plus `/usr/sbin`, `CC_x86_64_unknown_linux_musl=musl-gcc`;
removed afterwards.

**`box_has_no_network_but_loopback`.** A box without `egress`: curl
through `127.0.0.1:3128` exits 7, `Connection refused`; on Linux vsock CID 2
ports 1024 (exec), 4000 and 3128 each print `Connection reset by peer`
under a 5-second alarm. A box with one route: `/proc/net/dev` lists only
`lo`; `curl --noproxy '*' http://1.1.1.1/` exits 7, `Network is
unreachable`. Control: the route reaches the fixture (status 418, one
request seen); on Linux vsock 3128 connects.
Sabotage, macOS: drop `--network none` from `container run`
(runtime/apple.rs). Failed on `left: ["lo", "eth0"]`.

**`only_allowlisted_hosts_get_through`.** Allowlist `api.github.com`,
`localhost` and the host's own address (the source of its default route,
e.g. a LAN address); one route. CONNECTs to `localhost`, the host address
and `example.com` each get 403. `--connect-to
example.com:443:api.github.com:443` exits 35. The log holds one refusal
each: `example.com` `not allowlisted`; `localhost` and the host address
two different reasons, neither `not allowlisted` (observed: `loopback`
and `ip literal`); and one for `api.github.com` (observed: `sni mismatch`).
Control: the CONNECT to `api.github.com` gets 200 and curl completes
(GitHub's own status is not asserted: shared CI addresses can be
rate-limited); a DELETE to
`http://fixture.internal/a/b?SENTINEL` with `Host: evil.example` reaches
the fixture as DELETE with `Host: fixture.internal`; its log line names
DELETE, `/a/b` and 418, and the sentinel is nowhere in the log.
Sabotage, macOS: skip the refused-address loop in `network::resolve`.
Failed on localhost's CONNECT: 200, not 403. A second sabotage, skipping
the SNI comparison in tls.rs, failed on curl exit 60 (certificate) instead
of 35.

Observed: deleting only the loopback checks in `forbidden_v4` and
`forbidden_v6` does not fail the test. The host resolves `localhost` to
`::1` as well, and `::1` is also refused as the IPv4-compatible `0.0.0.1`.
The refusal stands, logged `unspecified`. Likewise, deleting the CONNECT
`ip literal` check does not fail it: the host address is then resolved
and refused as `private`. The observed reasons were confirmed by hand on
macOS with the same spec.

Row 1's Linux sabotage (a listener on the proxy's vsock port without
`egress`) is named in the test but was not run. The exec-port and
unused-port vsock probes run in the no-egress box only.

## Spec gaps

- Row 2 says each allowlisted refusal is logged "with its own reason", but
  the spec names no tokens for them. `loopback`, `ip literal` and
  `sni mismatch` are the binary's words, so the test asserts only that
  they are distinct and are not `not allowlisted`.

## Shared machine

Before and after, on the Mac: the user's box and its two volumes were
unchanged, and `container image list` was byte-identical. Every `box up`
with fresh roots runs daily maintenance against the shared runtime.
