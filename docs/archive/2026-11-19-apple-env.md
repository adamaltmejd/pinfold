# Apple box environment after boot

2026-11-19. Issue #351: on Apple, pinfold passed every box variable to
`container run --env` as `PINFOLD_BOX_ENV_<NAME>=<hex>`, and `container`
1.7.1 kept them in the box's `config.json` and
`runtime-configuration.json` (0644) and in `container inspect` while the
box ran. No test was added: the suite is suspended.

## Built

- `apple::up` passes no box variable to `container run`. It encodes the
  same list (spec, `from` values, always-applied names, the share
  `GIT_CONFIG_*` entries) as one ENV frame, the payload Linux's
  `vsock::set_env` sends. `Client::ready` writes it to the attached
  stdin from its own task and keeps stdin open as before.
- Apple's PID 1 (`init` without a verb) reads the frame before ready,
  checks it decodes, binds the abstract unix socket `pinfold-env` and
  serves the frame to each connection on its own thread. Ready now means
  the environment is held. A failed read fails the start.
- `init exec --box-env` (every Apple `exec_command` caller: `box exec`,
  crossing, disk export, launch, rex) and `init session-exec` (project
  commands) read the frame from that socket and apply it over the image's
  environment that Apple gives every exec.
- Shared pieces moved, not copied: `ENV` to `exec_wire`, the payload
  encoder to `exec_transport::env_payload`, the decoder to
  `firecracker::decode_env`.
- Deleted: `apple::guest_env` and its hex `--env` path; `session-exec`'s
  decoding of `PINFOLD_BOX_ENV_*` from its own environment.
- Kept: `PINFOLD_BOX_ENV_` as the in-guest hand-off from the exec service
  (Linux, and Apple's session exec through `firecracker::exec`) to its
  `init exec` child. It never leaves the guest's process environment. It
  is what lets a box variable named `PINFOLD_EXEC_METADATA` arrive;
  removing it would change Linux for no gain here.
- All variables, the non-secret always-applied ones included, take the new
  path: separating them would have kept a second mechanism.

## Choices

- **Abstract socket, not a file.** A `/tmp` socket is box-writable and
  could be replaced; an abstract name has no file and PID 1 holds it from
  before ready, so no box process can take it first. Any box process can
  read the environment there, as it already could from `/proc/1/environ`
  of the old transport; box work has the same uid as PID 1 on Apple.
- **Stdin, not a new exec.** The attached stdin already exists, needs no
  privilege and is read before anything runs in the box.

## Setup

macOS 27.2, Apple `container` 1.7.1, debug build of this branch. Private
XDG roots under the session scratchpad, `PINFOLD_NO_UPDATE_CHECK=1`,
`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `PINFOLD_PROFILE`
unset. Images: `debian:trixie-slim` and, where curl was needed,
`localhost/pinfold/profile-default:latest`, both already in the shared
store and only run. Dummy values: `dummy-lit-351q`, `dummy-from-351z`,
`dummy-tlit-351k`, `dummy-tfrom-351w`, `dummy-penv-351m`,
`dummy-hdr-351h`.

Each scan, run while the box ran and a session was live, first checked
that `container inspect BOX` exited 0 and Apple's directory for the box
listed 11 to 13 files, then counted the plain value and its hex in
`container inspect BOX`, in `grep -rlI` over
`~/Library/Application Support/com.apple.container/containers/BOX/`
(`config.json`, `runtime-configuration.json`, `kernel.json`,
`options.json`, `rootfs.json`, `service.plist`, `stdio.log`,
`vminitd.log`; `-I` skips the binary `rootfs.ext4`, `initfs.ext4` and
`kernel.bin`), in `ps -axww -o args`, in `grep -rlI` over the private
state, cache, config, data and runtime roots, which hold the launch
records, and over the host ownership directory `/private/tmp/pinfold-501`
(sockets and name locks, shared with the user's own boxes; read only).

## Observed

- **Positive control (origin/main 8c539bc).** Same `box up` spec: the hex
  of `dummy-lit-351q` and of `dummy-from-351z` each appeared once in
  `container inspect` and in two of Apple's files. Plain values: none.
- **`box up` spec env (this branch).** Spec with a literal, a `from`, a
  multiline value, an empty value, `PINFOLD_BOX_ENV_X`,
  `PINFOLD_EXEC_METADATA` and `NODE_USE_ENV_PROXY = "0"`. `box exec`:
  `PF_FROM=dummy-from-351z`, `PF_LIT=dummy-lit-351q`, `PF_ML` with both
  lines, `PF_EMPTY` set and empty, `PINFOLD_BOX_ENV_X=pref`,
  `PINFOLD_EXEC_METADATA=meta`, `NODE_USE_ENV_PROXY=1` (always-applied
  wins), the image's `PATH`. `box exec --tty` read the same values. Scan:
  zero everywhere, plain and hex.
- **Project (share, explicit image, profile `default`).** Configuration
  `env` with literal `PF_TLIT`, `PF_TFROM = { from = "PF351_TSRC" }`, a
  multiline and an empty value; `PINFOLD_ENV_PF_PENV` in the caller.
  After `pinfold start`: a non-interactive command, an interactive
  command (`test -t 0` true in the box), a second client joining while the first session ran, and
  `pinfold box exec` on the project box each saw `PF_TFROM`, `PF_PENV`
  and `PF_TLIT`; the multiline value was intact and the empty one set;
  `HOME=/home/pi`. Scan: zero for the `from` and `PINFOLD_ENV_` values,
  plain and hex. The literal's plain form appeared in one file, the
  project's `pinfold.toml` that holds it; nowhere else. The launch record
  named the variables only. The owner directory held neither form.
- **Share Git entries.** The same project, a Git repository, declaring
  `GIT_CONFIG_COUNT = "1"`, `GIT_CONFIG_KEY_0 = "user.name"`,
  `GIT_CONFIG_VALUE_0 = "pf351-user"` in `env`: the box saw
  `GIT_CONFIG_COUNT=2`, the declared entry and `safe.directory` at the
  share's guest root as entry 1. With `profile-default`'s image, `git config
  user.name` printed `pf351-user` and `git status --short` listed the
  host's untracked file, exit 0.
- **Egress.** `box up` with `allow = ["api.github.com"]`, a host-service
  route and an injecting route to a host fixture on `127.0.0.1:18351`
  with `Authorization` from `PF351_HDR`. In the box: `HTTPS_PROXY` and
  `http_proxy` set, `http://svc/a` reached the fixture without a header,
  `http://inj/b` reached it with `Bearer dummy-hdr-351h`,
  `api.github.com` 200, `example.com` refused. Scan for the `from` value
  and the header value: zero.
- **Large environment.** A 120 000-byte value (over the pipe buffer)
  arrived whole. A 300 000-byte value was delivered, but the guest
  kernel's per-string `execve` limit refused it at exec (`Argument list too
  long`), as it would on Linux.
- **Failed start.** With the box listed by Apple but not yet ready
  (`stopped`, its directory present): SIGTERM to `box up` ended with
  `down` reason `signal`; SIGKILL of the `container run` client ended with
  `failed`, `box exited before ready: signal: 9`. Both times `container
  list --all` had no box and the box's Apple directory was gone.
- **Linux smoke** (dev VM, Debian 13, Firecracker, musl debug build of
  this branch, private roots, a `FROM debian:trixie-slim` image). The same
  spec env: `box exec` printed the same values as on macOS. `grep -rlI`
  of the `from` value and its hex over the private roots, `/tmp` and
  `/run/user/<uid>`, and `ps -eww -o args`: zero.

`cargo clippy -p pinfold --all-targets --locked --target
x86_64-unknown-linux-musl -- -D warnings` (zig as ring's C compiler) and

## Not run

- Login routes: they add no box variable, only generated mounts and the
  proxy variables the injecting-route run covered.
- Apple's images, snapshots and volumes were not searched. The values no
  longer reach the runtime's arguments, environment or configuration, only
  the attached stdin, which `container` does not log (`stdio.log` held
  init's `ready`); a guest process may still write a value to a disk.
- Crossing, disk export, the launch helper and Rex's `rex-dial`, which use
  the same `init exec --box-env` as `box exec`, were not run.
- The `container run` client still inherits the owner's environment, as
  every child does, so the `from` source variables and `PINFOLD_ENV_*`
  sit in that process's memory, as on origin/main. pinfold passes none
  of them to the runtime, and the origin/main control showed Apple
  records no inherited plain value.
- A box started by an older pinfold cannot be exec'd by this one (no
  socket); no migration, by project rule.
