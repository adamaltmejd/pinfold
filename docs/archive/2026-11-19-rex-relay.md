# Rex relay through the real CLI, 19 November 2026

Ticket #336. The builder ran the debug binary of branch `rex-relay-336`
on the operator's Mac: Apple `container` 1.7.1, host Rex CLI
0.1.0-preview.21 (API revision 18). `rex.client.remoteControl` read `0`
and was not changed. The trial used private XDG roots, a temporary Git
project with a share, and a Rex tab created for the trial in the builder's
own session. Interactive starts were typed into that tab and read back
with `rex capture`.

## Image

A throwaway image built from `localhost/pinfold/profile-default:latest`
with `RUN curl -fsSL https://pkgs.superlogical.com/rex/install.sh | sh -s
-- --tarball` through `pinfold image build rex-trial-336`. The download
needed no login. The guest `rex` was installed at `/usr/local/bin/rex`.

## Cases

| Case | Observed |
|---|---|
| `pinfold start` in the Rex tab, image with `rex` | Exit 0. Stderr: `pinfold start: rex: in the Rex app, add unix:///private/tmp/pinfold-501/<64 hex>.rex once under Add Remote Host…` and `pinfold start: rex: the host is reachable while this project's box runs.` The socket was `srw-------`. |
| Host `rex --autostart=false -S unix://<path> ls`, then `new t336` | Listed the guest server's sessions; `new` created `t336`. Text sent to its pane printed the box's hostname. `rex ls` run inside the box through `pinfold --` listed `t336`: guest agents reach the same server at Rex's default path. `whoami` through the relay reported the listener `unix:///home/pi/.local/state/rex/run/server.sock`. |
| Second `start` | Printed the same two lines. Same socket inode, one guest server exec. |
| `stop` with a held connection | `stop` exited 0. The held connection read EOF. The socket was gone; `rex -S` reported no server. No `container exec` remained. |
| SIGKILL of the owner with a held connection | The held connection read EOF; no `rex-dial` exec remained. The socket file stayed and `rex -S` was refused. The guest server's `container exec` client stayed with the orphan box. |
| Next `start` after the kill | Removed the orphan box, started a new generation and printed the two lines. New socket inode. The orphan's server exec was gone. Through the relay, `whoami` reported a server started with the new box; `t336` was restored from the home disk. |
| `env -u REX_SESSION pinfold start` | Exit 0, nothing printed, no socket. |
| `pinfold start </dev/null` | Exit 0, nothing printed, no socket. |
| Image without `rex` (`profile-default`) | Exit 0, nothing printed, no socket, no exec left. |

The trial binary started the guest server with the project as its working
directory; a new guest pane still opened in `/home/pi`, so the committed
code drops that working directory. That change was not rerun.

A stale guest socket on the persistent home disk did not stop the next
generation's server.

## Finding during the build

The first relay passed bytes but every Rex handshake stalled about five
seconds until the client gave up. A Python relay through plain
`container exec -i … init rex-dial` stalled the same way, while plain
`container exec` echoed a line at once. Replacing std's `io::copy` in
`init rex-dial` with a plain read and write loop fixed it. The cause inside
`io::copy` was not isolated.

## Not run

- Remote Control on. The preference is read through one fixed `defaults`
  call; pinfold has no seam to point it elsewhere, and the user's value was
  not changed.
- Add Remote Host and native attach in the app, child panes seen from the
  Mac, and whether the app reconnects when a later start recreates the
  socket. These need clicks in the app.
- A newer Mac app against an older guest server.

## Cleanup

The project was stopped, its home disk removed with `pinfold disk rm`, the
image removed by exact name, the trial tab closed, and the temporary
project and XDG roots deleted.
