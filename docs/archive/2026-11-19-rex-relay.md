# Rex relay through the real CLI, 19 November 2026

Ticket #336. The builder ran the debug binary of branch `rex-relay-336`
on the operator's Mac: Apple `container` 1.7.1, host Rex CLI
0.1.0-preview.21 (API revision 18). `rex.client.remoteControl` read `0`
and was not changed. The trial used private XDG roots, a temporary Git
project with a share, and a Rex tab created for the trial in the builder's
own session. Interactive starts were typed into that tab and read back
with `rex capture`.

## Image

A throwaway image built from `localhost/pinfold/profile-default:latest`
with `RUN curl -fsSL https://pkgs.superlogical.com/rex/install.sh | sh -s
-- --tarball` through `pinfold image build rex-trial-336`. The download
needed no login. The guest `rex` was installed at `/usr/local/bin/rex`.

## Third trial, after the review of #345

Changes since the second trial:
- The connect probe is gone. A bootstrapping owner removes a left socket
  under the launch lock. `stop` removes it holding the launch lock after
  discovery finds no owner. A relay-less start that joins a running owner
  touches nothing.
- The owner waits for the guest server to accept, rereads Remote Control,
  then binds.
- Shutdown cancels pending setup.
- A finished server exec ends the relay.
- `start` waits up to 30 s for the Rex answer.

The trial used a fresh image, project, XDG roots and two Rex tabs, all on
commit `fc15fbb`.

| Case | Observed |
|---|---|
| `start` | The two lines. An immediate host `rex -S … ls` answered. |
| `ls`, `new t1` | Empty, then `t1`. |
| Held connection | `rex -S … events` stayed connected 62 s and then printed `session_created … (t60)`. |
| Second `start` | The two lines, same socket inode. |
| Host client SIGKILLed mid-stream | `events` killed: its `rex-dial` exec was gone within 1 s. A raw client that sent half an HTTP request and closed: no `rex-dial` exec after 0.0 s. |
| Two concurrent `start`s on a fresh box | Both printed the two lines and exited 0. One box, one socket, one server exec. |
| Guest server killed inside the box, then `start` | After the kill, no server exec and `rex -S … ls` found no server. `start` printed the two lines. `ls` answered, and `whoami` reported a server started at that start. |
| `stop` 0.5 s after a Rex `start` on a relay-less owner | `stop` exited 0 first and run record `74777eb4…` ended with `signal`. The start then printed the two lines for a new generation (`ff5daf23…`, its box started 2 s later). This is a draining answer followed by a retry, as for any start racing `stop`. | `env -u REX_SESSION` start, `</dev/null` start, image without `rex` | Each on a fresh owner: exit 0, nothing printed, no socket. |

Owner loss, finding 3 of the review:
- The orphan box outlives its owner, as the spec allows on Apple.
- The guest server's `container exec` survives with the orphan box and
  ends when the box is removed.
- Dial execs end with the owner.
- Nothing was changed for this.

Linux: the branch was built on the dev VM, which runs Debian with kernel
6.12. A one-line image build failed there with `builder exited before
handshake`, so no box ran. In a Git project whose image is missing,
`pinfold start` under `script`, with and without `REX_SESSION`, printed
identical `image-missing` lines and exited 125 both times.

## Fourth trial, shutdown during setup

Changes since the third trial:
- A first start's inline setup now runs after synchronization and yields
  to stop, box exit, a signal and the client leaving.
- Dropping a relay, a cancelled close included, stops it and unlinks its
  socket.
- A setup that finishes after shutdown began is not answered.
- The extra socket pass in `stop` runs on macOS only. It reads the
  locator under the launch lock and runs no discovery.

A script in a fresh Rex tab typed `pinfold start` and polled `pgrep`. It
ran `pinfold stop` once the guest `rex --autostart=false version` probe
appeared (probe) or once the guest `rex server run` appeared (server).
After each start returned, it counted `.rex` files in the host directory
and `.rex` sockets in `lsof -U`. Fresh image, project and XDG roots.

| Case | Runs | Observed |
|---|---|---|
| `stop` during a first start's setup, at the probe | 4 | `stop` exited 0. Start printed `stopped (…)` and exited 125. No address, no socket file, no listener, no box. |
| `stop` during a first start's setup, at the server | 3 | Same. |
| `stop` racing a running relay-less owner's setup, at the probe | 3 | `stop` exited 0. The stopped generation's box was gone. The start retried and printed the address for a new generation. One socket and one listener, both gone after the next `stop`. |
| Same, at the server | 3 | Same. |
| `start`, host `rex -S … ls`, `stop` | 1 | Two lines, `ls` exited 0. After `stop`: no socket, no listener, `rex -S … ls` exited 4. |

The first build of this change created a fresh `box_.ended()` on every
heartbeat. On one of three runs, a stop request that was half read was lost.
`stop` printed `box teardown input failed` and exited 125, and the start
printed the address. One `ended` future across the loop fixed it: every
later run was clean.

## Fifth trial, stop across a first start

The review of `dc52502` found the same loss at the handoff: when setup
completed, the `ended` future was dropped, and a stop frame read in part
went with it. The stop reader is now cancel safe in the owner's claim:
an accepted stop connection and the bytes read from it stay in the claim
until the request is complete, so any dropped wait continues on the next.
This also covers the heartbeat loops that existed before Rex. The pinned
`ended` from the fourth trial is gone.

A script in a fresh Rex tab typed `pinfold start` on a fresh owner and ran
`pinfold stop` at one point per run: when the box appeared, a fixed delay
after the guest probe appeared, or as soon as the host socket appeared.
One second after the start returned it counted the project's boxes
(`container ls -a`), `.rex` files and `.rex` sockets in `lsof -U`.
Setup completed between 0.15 s and 0.18 s after the probe appeared.

| Stop point | Runs | Observed |
|---|---|---|
| Box appeared | 1 | `stop` 0. Start `stopped during startup`, 125. |
| Probe + 0, 0.03, 0.06, 0.09, 0.1, 0.12, 0.15 s | 7 | `stop` 0. Start `stopped (…)`, 125. |
| Probe + 0.18, 0.2, 0.21, 0.24, 0.3 to 0.8 s | 10 | `stop` 0. Start printed the address and exited 0 first. |
| Host socket appeared | 4 | Same as the row above. |

Every run: no box, no socket file, no listener afterwards.

## The stopping acknowledgement

`6c48c8b` sent the project stop's `stopping` line with one `try_write`.
That can return WouldBlock before Tokio has seen write readiness, and the
stopping client would then wait out its deadline. The line now goes out
through awaited writes bounded by one second, with the bytes written kept
in the claim like the read side. Main sent it with an awaited `write_all`
under the same one-second bound, after the read, in a future the owner
could drop.

On the Mac, ten `start`/`stop` pairs on a share project with the default
profile: every start and stop exited 0, each stop took 0.66 to 0.78 s, and
no box remained.

Linux, on the dev VM: the branch built. A disk project's `start` needed
the default profile image, and `pinfold build --profile default` failed
with `builder exited before handshake` followed by `pinfold build: the
BuildKit build failed`. That was with private XDG roots, a fresh project
and the user `agent` in group `kvm`. A build of `origin/main` (`37ab71b`)
failed with the same error. The VM has no pinfold image to reuse, so the
Linux cases did not run: the disk project cycle, ten stops during startup,
and two concurrent stops.

A retry ran on `c7461ee` with the VM idle: no other pinfold or
Firecracker process, and `free -m` showed 7146 MiB free of 7947 before
the build. The branch built. `pinfold build --profile default` failed the
same way after 12.6 s. The build recorded no log: the run directory held
`launch.json` (builder memory 2560 MiB, 2 vCPUs) and an empty
`egress.jsonl`, and the builder cache directory held `cache.ext4` and an
`unclean` marker. Free memory after the build was 5694 MiB. One build of
`origin/main` with fresh state and cache roots failed with the same two
lines and left the same `unclean` marker. The Linux cases still did not
run.

## Finding during the build

The first relay passed bytes but every Rex handshake stalled about five
seconds until the client gave up. A Python relay through plain
`container exec -i … init rex-dial` stalled the same way, while plain
`container exec` echoed a line at once. Replacing std's `io::copy` in
`init rex-dial` with a plain read and write loop fixed it. The cause inside
`io::copy` was not isolated.

## Not run

- Remote Control on. The preference is read through one fixed `defaults`
  call; pinfold has no seam to point it elsewhere, and the user's value was
  not changed.
- Add Remote Host and native attach in the app, child panes seen from the
  Mac, and whether the app reconnects when a later start recreates the
  socket. These need clicks in the app.
- A newer Mac app against an older guest server.
- The `rex-relay-failed` path, the readiness timeout, and Remote Control
  turning on between the two reads.
- A guest that stays silent after the host's end: the Rex server always
  closed at once, so the five-second reply bound never fired.
- A Linux box: the dev VM's image builder failed before handshake.

## Cleanup

After each trial the project was stopped, its home disk removed with
`pinfold disk rm`, the image tag removed by exact name, the trial tab
closed, and the temporary project and XDG roots deleted.
