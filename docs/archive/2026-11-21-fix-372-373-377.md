# Three small bugs (#372, #373, #377), 2026-11-21

Each was reproduced through the CLI before the fix. Runs on macOS used
debug builds of main at 40c7855 (`before`) and the branch (`after`), with
throwaway `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` under a
scratch directory outside any checkout, `PINFOLD_PROFILE=default`, and the
existing `profile-default` image. No image was built or removed.

## #377: `box prune` as a root's first command prints nothing

Reproduction: under root A, `box up` a box on the default image, SIGKILL
its `up` after `ready`, then `pinfold box prune` under a fresh root B.

| Binary | `box prune` under B |
|---|---|
| before | exit 0, no output; the runtime no longer lists the box |
| after | `{"box":NAME,"event":"pruned","owner":PID}`, exit 0; the runtime no longer lists the box |

Before, the daily pass ran first and removed the box without a line.

Fix: `box prune` joins the commands that skip the automatic pass
(`main.rs`, the spec's Maintenance list).

Test: row 8 (`losing_the_owner_fails_closed`). Every `TestEnv` spends its
root's pass when it is created, so the old test could not see the bug.
Its prune now runs with `XDG_STATE_HOME` set to a new directory, a root
whose pass is due. Nothing else runs in that root, so its pass never runs
outside the maintenance hold. With `prune` dropped from the skip list the
test fails at the `pruned` assertion (`box prune: Exec { code: 0, stdout:
"", stderr: "" }`); with it, it passes. The sabotage comment names both
changes. Row 8's text now says the prune runs in a root whose pass is due.

## #373: an owner's startup refusal reaches the client as `owner-unavailable`

The owner already reports a failed start to its client as
`Reply::Error { reason }` on the bootstrap stream. It sent `stopped` for
a signal or control stop and `owner-unavailable` for everything else. Its
own stderr line is written after that reply, when the client has stopped
draining, so it was lost too.

Reproduction: #358's residual case. In a share project (non-Git), the
init's own directory `artifacts/init/<sha>` is a symlink into the project.
`artifacts/init` itself resolves outside, so the client's protected-path
checks pass, and the owner's `mounts::prepare` refuses.

| Binary | `-- true` from the project root |
|---|---|
| before | `pinfold: owner-unavailable`, exit 125 |
| after | `pinfold: spec: the project box was refused at startup`, exit 125 |
| after, `start` | `pinfold start: spec: the project box was refused at startup`, exit 125 |

The `after` rows were rerun with a build of the branch's final code, in a
fresh root, taking the init directory's name from a control run first.

A temporary debug write in the owner (not committed) showed the error:
`Refused { reason: Spec, detail: "host-path-in-project: …/initdir/linux-arm64 overlaps …" }`.
Control: the same project without the symlink runs `true`, exit 0,
before and after the case. The init directory inside the project stayed empty.

Fix: on `UpError::Refused` the owner sends the refusal's reason token
(`RefusalReason::token`), never its detail. The client accepts only a
token that parses as a `RefusalReason` and reports it; any other unknown
reason stays `owner-unavailable`. Exit code 125 is unchanged (project
setup failures use 125). Other owner startup errors (`UpError::Other`)
still send `owner-unavailable`. The spec's Admission paragraph says so.
Only the owner's failed-start reply can carry a refusal token: every other
`Reply::Error` sender writes `config-changed`, `session-protocol` or
`share-no-crossing`.

Not fixed: core wraps `mounts::prepare`'s protected-path failure as a
`spec` refusal, so this case prints `spec`, not `host-path-in-project`.
Naming it would mean string-matching the detail or a new `RefusalReason`,
which changes the public `refused` line. Left as is.

Two cases met on the way that are not owner refusals:

- A public `box up` holding the project's home disk: the client's own
  discovery finds a live claim with no project locator and refuses
  `owner-unavailable` before any owner starts. Unchanged.
- `cpus = 1000` in the project configuration: Apple's runtime fails the
  start (`box exited before ready: … cpus must be between 1 and 10 …`), an
  `UpError::Other`, so the client still prints `owner-unavailable` and the
  runtime's message is lost. Unchanged; it is not a refusal.

No test: no guarantee row covers a project client refused by its owner.
Row 48 refuses `host-path-in-project` in the client, before any owner.

## #372: a fresh disk project's subdirectory exits 125

Reproduction: a Git project with one commit and `sub/`, configured with
`mounts = [{ host = ".", kind = "disk" }]`, `pinfold -- pwd` from `sub/`.

before, macOS:

```
pinfold init exec: working-directory: sub below …/repo372: No such file or directory (os error 2)
exit=125
```

after, macOS:

```
pinfold init exec: working-directory: sub below …/repo372: No such file or directory (os error 2). If this is a disk project, run from the project root, or push the branch with `git push box BRANCH` and run `git switch -c BRANCH host/BRANCH` in the box
exit=125
```

Control: `-- pwd` from the project root prints the root, exit 0.

Fix: init's working-directory walk appends the remedy only for `NotFound`.
A symlink component (`ELOOP`) or an escape keeps the old message. The
`working-directory` prefix and exit 125 are unchanged. The wording reuses
`--help`'s `git switch -c BRANCH host/BRANCH`. No spec change: the spec
already makes a missing directory a setup failure, and the text is prose.
No test: the change is prose, which tests never assert.

The push-then-switch remedy itself was not run by hand here: the session's
tooling refused host `git push` outside its worktree. Row 10 covers the
push.

Linux, on the dev VM (Debian 13, x86_64): the same reproduction with
release musl builds of main (`before`) and the branch (`after`), in a
fresh clone from a `git bundle` at `~/pinfold-e2e-fix372`, `TMPDIR` in
`~/pinfold-e2e-fix372-tmp`, the suite's cache root for the default image.
First-run setup there picks a disk. `before`: the same `working-directory:
sub below …: No such file or directory (os error 2)`, exit 125. `after`:
the same line plus the remedy, exit 125. Control: from the root, exit 0.

## Review fixes

- #373: after sending the refusal reply the owner returned the error, and
  `cli::report` wrote its detail (host paths) to the owner's stderr. The
  client drains that pipe until the reply arrives, plus whatever is
  already buffered when it stops, so the detail could reach it depending
  on ordering. The owner now exits 125 after a refusal reply without
  reporting the error. Final build, same case as above: eight `-- true`
  runs each printed exactly `pinfold: spec: the project box was refused
  at startup`, exit 125; three `start` runs the same with `pinfold start:`.
  Control before and after: exit 0.
- Spec: the Admission sentence claiming every other owner startup failure
  is `owner-unavailable` was dropped. A host failure before any reply
  (for example at `state::record_run`) reaches the client as EOF, not as
  that token. The sentence is back to "Unavailable ownership refuses as
  `owner-unavailable`". No behavior change.
- #372: the remedy named a remote `box`, which setup no longer creates
  and which could name another server. It now reads: run from the project
  root, or push the branch into the box through a pinfold Git remote
  (`pinfold --help`, Disk projects) and check it out there. Rerun on
  macOS: the new line, exit 125; from the root, exit 0.

The throwaway roots, projects and their three disks were removed.
