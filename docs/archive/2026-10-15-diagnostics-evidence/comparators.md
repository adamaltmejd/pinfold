## What each comparator actually contributes

### Matchlock: an SDK need not replace a process boundary

The Go SDK starts `matchlock rpc` as a subprocess and uses JSON-RPC on stdin/stdout. Requests have IDs; stream notifications carry the originating request ID. Exec stdout/stderr and log streams are distinct notification methods. Context cancellation sends a cancel RPC for the outstanding request. `Close` closes the sandbox/process; `Remove` separately removes stopped VM state. This is directly relevant evidence that typed client ergonomics and process isolation can coexist. It does not demonstrate that Pinfold needs a multiplexed RPC protocol: Pinfold already separates lifetime ownership (`up`) and command IO (`exec`).

Source: [client.go](https://github.com/jingkaihe/matchlock/blob/77e02f643e72dbdaf3af295103a42343a330645e/pkg/sdk/client.go), [protocol.go](https://github.com/jingkaihe/matchlock/blob/77e02f643e72dbdaf3af295103a42343a330645e/pkg/sdk/protocol.go), [exec.go](https://github.com/jingkaihe/matchlock/blob/77e02f643e72dbdaf3af295103a42343a330645e/pkg/sdk/exec.go).

The implementation also demonstrates pitfalls a Pinfold wrapper should avoid. `NewClient` drains subprocess stderr to `io.Discard`. The sole response reader invokes request notification callbacks synchronously. `ExecStream` and `LogStream` write to caller sinks without propagating writer errors. Thus a blocked sink can stall dispatch for other requests on this reader; this is a source-derived risk, not a reproduced deadlock. Cancel is sent but the client returns `ctx.Err()` without waiting for confirmed remote completion. RPC error codes distinguish VM, exec, file, and cancellation categories, but the reviewed envelope carries code/message rather than a richer phase/provenance model.

Source: [protocol.go](https://github.com/jingkaihe/matchlock/blob/77e02f643e72dbdaf3af295103a42343a330645e/pkg/sdk/protocol.go), [log.go](https://github.com/jingkaihe/matchlock/blob/77e02f643e72dbdaf3af295103a42343a330645e/pkg/sdk/log.go), [RPC handler](https://github.com/jingkaihe/matchlock/blob/77e02f643e72dbdaf3af295103a42343a330645e/pkg/rpc/handler.go).

Matchlock's lifecycle runbook describes versioned persistent lifecycle rows, failure phases, owned resources, cleanup-step results, and reconciliation before metadata deletion. Its SDK intentionally preserves state after close. The relevant lesson is retaining evidence of incomplete cleanup, not copying its SQLite allocator/state machine: Pinfold's runtime ownership and resource footprint differ. [Lifecycle runbook](https://github.com/jingkaihe/matchlock/blob/77e02f643e72dbdaf3af295103a42343a330645e/docs/lifecycle.md).

### Docker: explain the effective decision, preserve uncertain outcomes

Local `sbx policy ls/inspect/log` exposes rule origin/scope and matched rule/reason/proxy path. Structured traffic entries include sandbox ID and first/last seen/count. These are aggregated recent observations, not a complete per-request causal trace. The cloud cookbook explicitly separates effective policy from recent traffic and warns that no log entries do not prove reachability. [Monitoring](https://docs.docker.com/ai/sandboxes/governance/monitor-and-enforce/monitoring/), [Effective policy cookbook](https://docs.docker.com/ai/sandboxes-api/cookbook/control-what-a-sandbox-can-reach/).

Published `dist/routes.d.ts` confirms an effective mode/allow/deny view plus an exact policy representation with revision and source origin/id; policy log entries include decision, rule, reason, counts, sandbox UID, and timestamps. A Pinfold equivalent can be much smaller: resolved immutable policy plus profile/default origins and effective runtime/image identity. A general policy expression AST is unnecessary for Pinfold's simpler policy.

Docker documents structured error code/details rather than message parsing; failed waits retain the last resource and distinguish client cancellation from server completion. Resource identity is immutable and separate from display names. These are useful lessons for generation-safe handles and evidence that distinguishes “failed” from “outcome unknown.” [Errors](https://docs.docker.com/ai/sandboxes-api/errors/), [API concepts](https://docs.docker.com/ai/sandboxes-api/concepts/).

Implementation evidence in the 0.53.0 artifact: `dist/sandboxes-client.js:191-242` implements bounded command accumulation with `maxOutputBytes`, continues consuming subsequent chunks, and returns `incomplete`. It checks increasing `streamSequence` and consistency with `nextResumeFrom`. A failure after creation retains the process resource in `ResourceWaitError` and states it may still run. `dist/streams-common.js:332-351` caps WebSocket receive queues/frames and fails visibly rather than silently dropping. These are useful requirements for a thin Pinfold SDK. They do not imply Pinfold needs a server, reconnect protocol, or cloud resource layer.

### E2B: separate connection failure, process outcome, and sandbox death

E2B's lifecycle documentation distinguishes sandbox lifetime from individual stream lifetime. Existing commands can be reattached by PID after disconnect. Its lifecycle-events API documents seven-day default retention, event IDs/version, sandbox identity, execution/build/template IDs, timestamps, and event data such as kill reason. This explicitly connects postmortem evidence to an execution rather than only a user-facing name. [Lifecycle](https://docs.e2b.dev/sandbox), [Stream lifetime](https://docs.e2b.dev/faq/sandbox-lifetime), [Events](https://docs.e2b.dev/sandbox/lifecycle-events-api).

Current `CommandHandle` source retains stdout/stderr and raises `CommandExitError` with exit code and both streams on nonzero exit. `disconnect()` stops receiving without killing the command; `kill()` is a separate SIGKILL operation. Missing terminal result becomes an error rather than success. Errors distinguish sandbox confirmed stopped from unreachable/unknown, acknowledging limits of health-probe evidence. However part of availability classification still parses proxy message substrings. Prefer native structured reasons in Pinfold rather than reproducing this translation burden.

Sources: [CommandHandle](https://github.com/e2b-dev/E2B/blob/62a17dfc3f11439d1d06bfb9bb515eadc5adfcd3/packages/js-sdk/src/sandbox/commands/commandHandle.ts), [errors](https://github.com/e2b-dev/E2B/blob/62a17dfc3f11439d1d06bfb9bb515eadc5adfcd3/packages/js-sdk/src/errors.ts).

`CommandHandle` appends all stdout/stderr to strings even while delivering callbacks. It awaits callbacks, providing consumer-paced iteration at that point, but that does not bound retained memory or prove server-side flow control. A streaming API by itself is not evidence of boundedness. The CLI has separate JSON/pretty sandbox log output. This review found network configuration in `SandboxInfo`, but did not establish an effective-policy provenance or per-decision audit interface equivalent to Docker's. Do not convert that limited review into a claim that E2B lacks one.

### Daytona: preserve error origin, but distinguish available interfaces

The current SDK error envelope preserves HTTP status, machine code, source (`DAYTONA_API`, `DAYTONA_DAEMON`, `DAYTONA_PROXY`), and headers. Classification prioritizes `(source, code)` over HTTP status. Local validation and connection timeout are separate. Its timeout message explicitly says already-started server work may continue. This is a useful small model for distinguishing Pinfold admission/runtime/proxy/exec failures without implying that every layer needs its own exception class hierarchy. [Error implementation](https://github.com/daytona/clients/blob/82b53c9cbb4abb8a0505411e8b15c01085d3b94a/sdk-typescript/src/errors/DaytonaError.ts).

Session execution exposes session/command IDs, stdout/stderr, exit status, snapshot logs and streamed logs. The simple TypeScript `executeCommand` wrapper instead returns a combined `result` and maps it into `artifacts.stdout`; do not claim all Daytona exec paths preserve streams. Session log streaming invokes callbacks from a WebSocket demultiplexer; this high-level overload offers no AbortSignal parameter. The documentation warns blocking Python callbacks can disconnect WebSockets. [Process implementation](https://github.com/daytona/clients/blob/82b53c9cbb4abb8a0505411e8b15c01085d3b94a/sdk-typescript/src/Process.ts), [Stream demultiplexer](https://github.com/daytona/clients/blob/82b53c9cbb4abb8a0505411e8b15c01085d3b94a/sdk-typescript/src/utils/Stream.ts), [Log streaming docs](https://www.daytona.io/docs/en/log-streaming/).

Daytona documents audit records keyed by actor/action/target/status and state-change webhooks. These are distinct from command output and policy decisions. The reviewed docs do not establish guaranteed webhook delivery or a post-deletion output-retention contract. [Audit logs](https://www.daytona.io/docs/en/audit-logs/), [Webhooks](https://www.daytona.io/docs/en/webhooks/).

## Architecture implications for Pinfold (inference)

1. Keep the binary as the enforcement authority and the subprocess interface as the integration boundary. None of these comparators demonstrates that Pinfold's local diagnostic problems require embedding the core or adopting a daemon/service. Matchlock specifically shows an SDK can wrap a binary.
2. Improve evidence at its origin before wrapping it: structured operation/phase/reason; lifetime identity/generation; effective nonsecret policy and image/runtime identity; explicit unknown/unavailable/incomplete outcomes; retained bounded teardown evidence. A typed SDK cannot recover detail already flattened into prose or deleted on teardown.
3. A thin SDK should own only process IO, bounded buffering, parsing, typed results, signal/cancellation handling, and lifecycle cleanup appropriate to the existing `up` contract. Keep raw command stdout/stderr separate from lifecycle/diagnostic records. Avoid introducing multiplexed RPC solely to obtain typing.
4. Distinguish canceling the wait, canceling an exec, and ending the box. A result must say what is confirmed. Do not infer teardown from losing a connection or from an SDK timeout. Pinfold's stdin-owner lifetime differs intentionally from cloud resource lifetimes; document that difference rather than importing cloud pause/resume semantics.
5. Bound diagnostic buffers and command capture independently. Preserve truncation/incompleteness metadata; keep draining or propagate intentional backpressure according to a stated contract. Do not silently discard owner stderr. Test slow/no readers at the real CLI boundary before claiming responsiveness.
6. Preserve postmortem evidence independently of disposable runtime state, with explicit retention/size/redaction rules if the user chooses this guarantee. Do not copy Matchlock's whole database, Docker's policy AST, E2B retention duration, or Daytona audit platform. The requirement is answerable incidents, not feature parity.
