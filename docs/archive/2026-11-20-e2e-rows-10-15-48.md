## Cleanup on a shared Mac

Read from core/clean.rs and cli.rs's `CleanPlan` before row 15 was
written. Under a throwaway state, config and cache root, `clean --unused
0s` removes:

- dead pinfold boxes host-wide and leftover ownership records and sockets
  (as `box prune` and the daily pass do; only boxes whose owner is gone);
- unpinned artifact versions and retired run records of its own roots;
- the state directory and disks of its own root's idle projects (the
  project id comes from that root's `projects/`; disks belong to one state
  root, Disks);
- on Apple, the shared BuildKit cache: `container exec buildkit buildctl
  prune --all`, then `container clean buildkit` (runtime/apple.rs
  `purge_build_cache`); on Linux, the idle builder cache in its own cache
  root;
- `keep_two_images(service, None)`: in every source any listed image
  names, build tags past the newest two. On Apple that is the host-wide
  image store, so a user's older `profile-*` or `project-*` builds go.

So on the Mac `clean` can remove images the test did not create and prunes
the user's build cache. Row 15 is `#[cfg(target_os = "linux")]` (main.rs
says why). On Linux images and the builder cache live in the suite's cache
root. Its Apple clause ("leaves a share project's host files, an
externally started container and an unlabeled image untouched") is not
implemented or run, and stays in the row unproven.

The same `keep_two_images` pass already runs on the Mac in every test:
`TestEnv::new` spends a fresh state root's daily maintenance pass, which
calls it on the host-wide store. Today every source in the store has
exactly two build tags, so nothing went, but the harness is not
root-scoped there either. For the operator to decide.

## Row 10's hostile listing

Crossing runs `sh -c SCRIPT` in the box, and the script calls `git` by
name (core/crossing.rs `FETCH_SCRIPT`). The image's PATH has no writable
directory, so the 2026-11-19 record built a hostile image. A user seam
does it without one: the project's `pinfold.toml` sets `env = { PATH =
"/home/pi/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
}`, and the box's env applies to crossing's execs as to sessions. A
session then writes `/home/pi/bin/git`, a script that runs `/usr/bin/git`
and, while `/home/pi/.hostile` holds an object id, appends `ID
refs/heads/stolen` to the branch listing (`for-each-ref
--format=%(objectname)… refs/heads/`). The fetches use the kept box
(`pinfold start`), so the home disk is there.

## Tests

**`disk_project_branches_and_tags_cross_only_through_the_git_remote`
(10).** Host: `main` at c1 with annotated `v1` and lightweight `light`; a
branch `secret` with a commit the box never gets. The configuration is a
disk with the PATH above.
- Fresh start: `.git/config` is byte-identical across `pinfold start`;
  `pinfold -- ls -A` prints nothing (both platforms; no `lost+found` on
  Linux).
- `git remote add box pinfold::ROOT`; `git push box main`: the box's
  repository then holds exactly `refs/remotes/host/main` at c1.
- The box writes the wrapper, checks `main` out, commits `.githooks/` and
  `.husky/` holding a hook under each of 18 client-side names (each would
  `touch` a file named for it in the host directory `planted`), tags
  annotated `box-new` and lightweight `light`, commits a branch
  `feature`, and sets its own `core.hooksPath = .githooks`.
- (a) With `.hostile` holding `secret`'s id, `git fetch box` exits 128:
  `pinfold remote: branch "stolen" names ec67…, which is neither a
  verified bundle head nor reachable from refs/remotes/box/*`. The box's
  new commits made a real bundle. Every host ref and the `.git/objects`
  tree (paths, lengths, mtimes) are unchanged. The test asserts the token
  `stolen`.
- (b) `git fetch --force --tags --prune --prune-tags box`: the host's tags
  are `v1` and `light` where they were, plus `box-new` at the box's id.
  Control: `box/main` and `box/feature` at the box's ids.
- The host's own `post-merge` and `post-checkout` hooks write to
  `host-ran`. Twice (the box commits again in between): `git fetch box`,
  `git merge box/main`, `git checkout -b ROUND`, `git checkout main`.
  `host-ran` holds both names (control), `planted` is empty, and host
  `core.hooksPath` is unset.
- The host commits c2 and tags annotated `rel`. `git -c
  push.followTags=true push box main`: the box's refs are as before plus
  `host/main` at c2, `rel` and `v1` at the host's tag objects; its
  branches, its `light` and `box-new`, and the sha256 of every working
  tree file are unchanged.

Sabotage (macOS): skip `!carried && !reached(oid)?` in
`fetch_cancellable`. The hostile fetch exited 0 printing `* [new branch]
stolen -> box/stolen`.

Observed while writing it: the box's own hooks run for the box's ref
updates, the push's included. A planted `reference-transaction` hook that
failed in the box (its `touch` path does not exist there) failed `git push
box main` with `pinfold: the box's git failed` and every ref `remote
rejected`. That is Git: the box repository's hooks and config are the
box's (Git), and the push prints none of the box's text. The planted hooks
now exit 0.

**`a_share_reaches_only_its_folder_and_a_protected_path_is_refused`
(48).** The project selects a user profile `e2e-base` whose
`pinfold.toml` is `base = "default"`, so it runs on default's image with
no build. In turn, the project's configuration directory and the
profile's directory are moved into the checkout as `linked` and replaced
by a symlink to it. `-- true` exits 125 and `config edit` exits 1, each
with `host-path-in-project` on stderr; the state and config roots' trees
are unchanged. Restored, the same project runs `-- true`, exit 0.
Observed: the configuration case and both `config edit`s say
`…/linked resolves inside ROOT`; the profile case's `-- true` says
`overlaps` (share admission's bidirectional check). Not asserted.

On macOS, in a running share: `out` is a symlink to a host file outside
the project. In the box `readlink out` prints that path; `open` of `out`,
of the absolute path and of `../outside/secret` each fail with errno 2;
`inside` reads `inside`. The box writes `edit` and runs `git commit`:
the host file holds `edit`, host `HEAD` is on `main`, `HEAD^` is the
host's commit and `HEAD:edit` is `edit`. On Linux the share half is
compiled out and the refusal runs for a disk project.

Sabotage (macOS): delete `paths.extend(extra)` in core/mounts.rs's
`protected_paths`. With the configuration directory linked in, `-- true`
ran and exited 0.

**`cleanup_removes_only_pinfolds_garbage` (15, Linux).** Two disk
projects. `live`: `pinfold start`, then one session writes `marker` and
ends, so the box is kept with no clients. `idle`: one `-- true`, then a
host file in its checkout. Each project's state directory
(`<state>/pinfold/projects/ID`, ID from `config --json`) and disk files
(`<state>/pinfold/disks/NAME.ext4`, names from `config --json`) exist.
Under the maintenance lock, `clean --unused 0s` exits 0. Then: `idle`'s
state directory and both disk files are gone (control); its checkout tree
and configuration file are unchanged; `live`'s are present, `box list`
shows the same generation, and `-- cat marker` prints `kept`.

Sabotage (Linux): dropping only the `!live.contains(&project.id)` test in
`CleanPlan::idle` passed: the kept owner holds the project lock, so
`try_project_lock` skips the project. Dropping that test and the
`locks.contains_key` skip in `CleanPlan::remove` failed: the live
project's state directory was gone after `clean`. The test names both.

Every sabotage was reverted; `git status crates/pinfold` was clean on both
machines.
