## Harness additions

`crates/e2e/src/lib.rs`:

- Every command the harness runs (`run`, and every `pinfold` and host
  `git` it builds) drops each inherited variable whose name holds
  `TOKEN`, `KEY`, `SECRET`, `PASSWORD`, `CREDENTIAL` or `AUTH`, and
  `CODEX_HOME`. `GIT_*` is exempt: dropping `GIT_CONFIG_KEY_n` alone
  breaks Git, and project commands drop the family already. A test's
  own variables must not match.
- `Fixture::model(reply)`: a fake model on the existing fixture. A
  request to `…/chat/completions` gets an OpenAI-compatible streamed
  completion of `reply`; one to `/v1/messages` gets Anthropic's streamed
  message; anything else an empty 200. Every request is recorded as
  before.
- `Project::unconfigured` (only `git init`) and `Project::configure`
  (`config edit`); `Project::new` is the two.
- `Client`: a spawned project client with piped stdin and stdout, killed
  on drop. `READER` is a session script that runs each line it reads
  with `sh -c`, stdin closed, and prints `done`; `Client::ask` sends a
  line and returns its output.
- `BoxUp::ended`: waits, bounded, for `up` to end on its own; its last
  line and exit code.
- `TestEnv::cache_home`.

## Host logins

pinfold reads no host login for these routes. Claude and Pi's
`openrouter` routes read their credential from the `from` variable
the test sets. Only a `codex` route, or Pi's `openai-codex`, runs the
pinned Codex helper, which reads the host's Codex store (`CODEX_HOME`
or `~/.codex`, core/login.rs); neither is used. The project owner
compares `HOME` and `CODEX_HOME` as host roots
(pi/session_snapshot.rs) but reads nothing there. `HOME` was left
alone: redirecting it would move Apple `container`'s own state. Every
credential the test uses is a random string it invents. Nothing read
`~/.codex`, `~/.claude`, Pi's files or a real key.

## Tests

**`credentials_stay_on_the_host` (26).** A share project (a disk on
Linux) whose configuration adds `allow = []`, an env `from` variable,
an env literal, an injecting route (`X-E2E-Key`, prefix `Key `), a
`claude` login route and a Pi `openrouter` login route, each `to` its
own host fixture; the client also sets a `PINFOLD_ENV_` value. Every
value starts `pfsecret`; route credentials start `pfsecretroute`. One
session (`READER`) holds the box while:
- `env` in the box holds the `from` and `PINFOLD_ENV_` values (control)
  and no route credential, plain or hex.
- The guest sends `x-e2e-key: pfbox-inject`; the fixture receives only
  `X-E2E-Key: Key <host value>`.
- Through the Pi route the guest sends `authorization` and
  `AUTHORIZATION` Bearer values, `x-api-key` and `X-API-KEY`, and
  `Connection: Authorization, X-Api-Key`. With `?api_key=pfbox-e` curl
  gets 403, the run's log gains one line `refused`, `login credential
  query`, and the fixture got nothing. Without the query (control) curl
  gets 200 and the fixture receives exactly `Authorization: Bearer <host
  value>` and no `X-Api-Key`.
- `claude -p 'Reply.'` and `pi -p --provider openrouter --model
  openai/gpt-4o-mini 'Reply.'` print their fixture's invented reply.
  Claude's one request went to `/v1/messages?beta=true`, Pi's to
  `/api/v1/chat/completions`, each with only the host credential.
- The box writes `pfsecretroutecanary` to `$HOME`, then greps every
  top-level directory but `/proc`, `/sys`, `/dev` and symlinks for words
  starting `pfsecretroute` or its hex, and prints them. The canary is
  among them, no credential is. The box is never told a credential.
- Host `ps` (`-axww` on macOS, `-eww` on Linux) shows the session's argv
  canary and no value, plain or hex.
- On Apple, `container inspect` of the project box names it and holds no
  value.
- A walk of the state, config and cache roots, and on Apple the box's
  directory under `~/Library/Application Support/com.apple.container/
  containers/`, finds the configuration's literal in `pinfold.toml` and
  nothing else. It reads only data extents (`lseek` `SEEK_DATA` and
  `SEEK_HOLE` through libc, no new dependency): a running box's Apple
  `rootfs.ext4` was 550 GB sparse with about 1.5 GB of data, and Linux's home disk 64 GiB.
  BSD `grep -r` over the same roots did not finish in 120 s. The run's
  egress log is under the state root.

Sabotage (macOS): set `login_policy` false in proxy.rs's `route`. The
query request got 200, not 403. Second sabotage (macOS): pass `&[]` for
`remove` to the plain-HTTP `forward`. The fixture got `x-api-key:
pfbox-c` and `pfbox-d` beside the host's `Authorization`.

**`every_egress_decision_is_recorded_or_the_box_stops` (38).** `box up`
with one route to a fixture, `allow = ["api.github.com"]`, an env literal,
2 CPUs and 1G. The cap is checked on the file's length
(`metadata().len()` in proxy.rs's `record`), so the test pads by
`set_len`, writing nothing.
- First run: a route request (418) and `http://example.com/` (403) add
  one `allowed` line and one `refused`, `not allowlisted` line. The log is
  then extended to 134217727 bytes. The next route request ends `up` with
  `down`, reason `audit-log`, exit 1. The log's length is unchanged and
  its first bytes are the two lines.
- Control: a second run of the same name has a new run id and a log of
  exactly its own two lines; the first log is unchanged.
- `box inspect` of the first run with `PATH` an empty directory exits 0:
  the launch record names the run, the box, the spec's allowlist and
  route (`host-service`, the fixture's address), `cpus` 2.0, `memory`
  `1G` and `E2E_LITERAL`, and nowhere the literal's value; the terminal
  record says `audit-log`; the log is 134217727 bytes.

The request that trips the cap may already have reached the fixture
(Egress proxy), so neither its answer nor the fixture is asserted.

Sabotage (macOS): skip the cap check in proxy.rs's `record`. The padded
log grew and `up` did not end within 120 s.

**`a_projects_sessions_share_one_box` (47).**
- An unconfigured Git project: `pinfold -- printf '[%s]' '' --help 'a b'`
  exits 125 with `no-config` on stderr, and the state and config roots'
  trees are unchanged. After `config edit` (control) the same command
  prints `[][--help][a b]`, exit 0.
- The configuration then adds `allow = ["api.github.com"]` and an env
  `from` variable. Two clients launch at once with the same value: A runs
  a background `sleep` and `wait`s; B runs `READER`. One printed
  `waiting for the project box to start`. `box list` for the project
  shows one box.
- Control: a third client with the same value joins and `cat`s both
  sessions' files from the box's `/tmp`. A client with another value
  exits 125 naming `config-changed` and `env.values`.
- Joined commands exit 23, 126 and 127 from `sh -c 'exit N'`; a missing
  executable exits 125.
- A's client is SIGKILLed. In B, `tail --pid` (bounded by `timeout 60`)
  sees A's shell and its background child exit. `box list` shows the
  same generation and owner.
- The file's allowlist is changed to `example.com`. From B,
  `example.com` still gets 403 (`not allowlisted`) and `api.github.com`
  200, each one line in the run's log.
- B's stdin closes and it exits 0.

Sabotage (macOS): drop the `env.values` comparison in
pi/session_snapshot.rs's `differences`. The client with another value
joined and `true` exited 0.

Every sabotage was reverted; `git status crates/pinfold` was clean
afterwards.

## Findings

- The launch record's `env` lists `PINFOLD_ALLOW`, which pinfold adds
  (Process interface: it defaults to the spec's allowlist). Run records
  says `env` "lists declared variable names only". The first version of
  row 38 asserted `env == ["E2E_LITERAL"]`, from that sentence, and
  failed: `pinfold box inspect RUN` printed `"env":["E2E_LITERAL",
  "PINFOLD_ALLOW"]` for a spec declaring only `E2E_LITERAL`. The test
  now asserts that the declared name is listed and no value appears,
  which is the row's own text ("env names without values"). This is a
  narrowed assertion, not a clean pass. The operator decides whether the
  binary or Run records is right; the exact assertion follows.
- On Linux the home disk image lies under the state root, so row 26's
  file sweep reads it. Should an agent ever write its environment to its
  home, the sweep would fail on the `from` or `PINFOLD_ENV_` value
  without pinfold being at fault (Always applied: what a guest process
  writes is its own).
- owner.rs (row 8) keeps its own small `Client`, beside the harness's
  new one. Left unchanged.
- #379 (row 11's refused `box up` not exiting) was not seen in any run.
