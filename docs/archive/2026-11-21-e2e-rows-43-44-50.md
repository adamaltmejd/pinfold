## Harness additions

`crates/e2e/src/lib.rs`:

- `TestEnv::own_cache(test)`: a test whose `XDG_CACHE_HOME` is its own
  directory, not the suite's. On Linux that is its own builder and image
  store. Its builds neither collide with the suite's (a second build on
  one cache root fails `builder-in-use` after a short wait, ownership.rs
  `Claim::take`) nor are emptied by row 15's `clean`. It starts cold every
  run, fetching the builder, VMM and kernel itself.
- `Below::named(name)`: the pids below an owner with that command name,
  so a test finds an owner's `firecracker`.

`crates/e2e/tests/e2e/main.rs`: the new modules `build` (44, Linux),
`chain` (50) and `jail` (43, Linux). libtest starts tests in name order,
so `build`, `chain` and `clean` start in the first batch, beside the
first test that builds the default image, rather than queued behind it.

## Tests

**`the_vmm_reaches_only_its_own_box` (43, Linux).** Box A is `box up`
with the default image and one 1G disk. Box B is a disk project kept by
`pinfold start`, so its owner is the detached `__project-owner`. Each
VMM is the one `firecracker` below its owner (/proc). For each VMM, from
the host:
- `/proc/PID/status`: every `Uid` and `Gid` field is the test process's
  own uid and gid; `CapBnd` 0; `NoNewPrivs` 1.
- `/proc/PID/ns/{user,mnt,pid,net,ipc,uts}` differ from the test
  process's and from the other VMM's.
- A walk of `/proc/PID/root`, not following links, holds the device and
  inode of its own disks' backing files (A's one disk; B's home and
  project disks, named by `config --json`) and of none of the other
  box's (control).
- No mount point in `/proc/PID/mountinfo` (field 5) is under `$HOME`.
- Every socket in the jail sits in the directory of the configuration's
  `vsock.uds_path` (read from the jail's `config.json`) and is named for
  that socket or `<socket>_<port>`, Firecracker's host-listener
  convention.
- Each owner's listening Unix sockets (its fds' socket inodes, named in
  `/proc/OWNER/net/unix`) that do not follow that convention have no
  entry by that name in the jail. The project owner holds at least two:
  observed `c.sock` (session control) and `<hash>.sock` (shutdown).
  pinfold binds them by name inside their directory (`bind_at`), so
  /proc names only the leaf, never a path; the check is therefore by
  name, not by inode.
- Control: SIGKILL of the detached owner; every process below it,
  the VMM among them, is gone (`Below::wait_gone`).

Sabotage (Linux): drop `CloneFlags::CLONE_NEWIPC` in
core/runtime/firecracker/jail.rs. Failed at the namespace check:
`assertion left != right failed: ipc`, both `ipc:[4026531839]`.

The mountinfo check reads mount points relative to the VMM's root, so
after the `pivot_root` it can only fail if the jail itself mounts
something at a home-like path. Without the pivot it fails only where the
state root lies under `$HOME` (pinfold's default layout and the dev VM's
`TMPDIR`), not where CI's `TMPDIR` is `/tmp`. It stays: it is the row's
"none of its mounts is under the home" and the 2026-10-20 jail check's
observation.

**`linux_image_work_stays_in_its_own_vm` (44, Linux).** Its own cache
root. The host resolves `example.com` and connects to its IPv4 address on
port 80 directly (control: the address is reachable). A caller image
(`image build`) `FROM debian:trixie-slim` has one heredoc RUN step,
in bash with no added tool:
- `timeout 20 bash -c 'exec 3<>/dev/tcp/<that address>/80'`: its exit and
  stderr;
- through `$http_proxy` (set by the builder), a plain HTTP `GET
  http://HOST/` to `api.github.com` and to `example.com`: the first status
  line.

The results are files in the image, read from a box of it. First build:
the direct connection exits 1 (not timeout's 124) with `Network is
unreachable`; `api.github.com` answers `HTTP/1.1 301 Moved Permanently`
(GitHub's redirect to HTTPS); `example.com` gets `HTTP/1.1 403 Forbidden`.
The egress log the build names on stderr (`build run …; egress log
PATH`) has one `refused`, `not allowlisted` line for `example.com` and
one `allowed` line for `api.github.com`. Control: the same recipe with
`--allow example.com --no-cache` (without `--no-cache` the RUN step is
a cache hit) gets `HTTP/1.1 200 OK` from `example.com`, one `allowed`
line for it, and the direct connection still fails the same way.

Sabotage (Linux): in core/image/linux/job.rs's `run_transaction`, push
`example.com` onto `hosts`. Failed: the first build's `example.com` got
`HTTP/1.1 200 OK`, not the 403.

**`a_profile_with_a_base_applies_it_and_is_outdated_when_it_changes`
(50, both).** Its own cache root. Three user profiles under the test's
config root, `e2e-<pid>-root`, `-mid` (`base` root) and `-top` (`base`
mid). Each recipe `FROM`s the link below's stable ref and adds one `RUN
echo NAME > /etc/e2e-NAME`. The root and the top seed `home/e2e-seed`
(`root`, `top`).
- With the root's `base` set to the top, `box up` with `profile` top (a
  home disk, `HOME` on it) is refused, reason `profile`. Corrected, `build
  --profile top` builds the chain and the same spec comes ready (control).
- A project with `profile` set to the top: `pinfold -- sh -c 'cat
  /etc/e2e-root /etc/e2e-mid /etc/e2e-top "$HOME/e2e-seed"'` prints
  `root mid top top` (control: every link's file and the top's
  replacement seed), with no `image-outdated` line.
- The root's RUN now writes `root-2`. The next launch exits 0 and prints
  an `image-outdated` line naming each of the three `:latest` refs.
- After `build --profile top`: no `image-outdated`, and the box reads
  `root-2`.
- A second, unchanged build keeps each link's image id, read from the
  `ready` line of a box of each `:latest` (three distinct, non-empty ids,
  equal before and after).

The root's base differs by platform. On Linux it is `debian:trixie-slim`,
in the test's own store. On macOS it is the default profile image:
`refresh_base` (core/image.rs) re-pulls a public `FROM` into Apple's
host-wide store before each build, which can move the user's
`debian:trixie-slim` tag; a pinfold-built base is never pulled. The
chain still has no `base = "default"`, so no agent install runs. This is
a deviation from "not built on `default`" taken for the shared Mac
store; the Apple half is proven on that footing only.

Sabotage (macOS): in pi/launch.rs's freshness walk, give `None` where a
base is itself outdated (`builds on an outdated image`). Failed: after
the root's change only the root named `image-outdated` (`left:
["e2e-94735-root"]`).

## Part C: row 26's unproven controls

Both were run against row 26 on macOS, then reverted
(`git status crates/pinfold` clean). The test was not changed; the two
sabotages are now named in its comment.

- **Lost body.** proxy.rs `forward`: copy no body
  (`Read::take(client, 0)`) and drop the guest's `Content-Length`. The
  control request through the Pi login route got `400`, not `200`
  (credentials.rs:422, `left: ["400"]`): the model fixture's answer to a
  POST without its prompt. The proxy's own refusal path was unchanged.
- **Authorization nomination.** proxy.rs `forward`: drop an injected
  field that the request's `Connection` value names. The nominating
  request reached the Pi fixture with no credential field
  (credentials.rs:450, `credential fields at the Pi fixture: []`). A
  first, broader sabotage (drop the injected field whenever `remove`
  holds it) failed earlier, at the control request (line 425), because
  `remove` always holds the fixed list; it showed nothing about
  nomination and was replaced.

## Test corrections

First-run expectations of mine that the binary or the runtime did not
meet. Each was mine to fix, not a finding:
- Row 44 first asserted an allowed line's reason as empty; the binary
  writes `allowlisted`. That word is not a spec token, so the test now
  asserts the decision of allowed lines only, and the reason only of the
  refusal (`not allowlisted`, a spec token).
- Row 50's seeds have no trailing newline, so `cat` prints none after
  the last one.
- Row 50's `box up` with `profile` needs `HOME` on a disk for the seeds;
  without it the corrected spec was refused `profile` for that reason
  (`the box spec has no exact HOME env entry`). The first run's cycle
  refusal could therefore not be told from this one, so the spec now
  carries `HOME` and a home disk in both.
- Row 43 first looked for the owner's control sockets by path; /proc
  shows only their leaf (above).

## Row 15 and the time budget

**Cause.** Row 15's `clean --unused 0s` ran with the suite's cache root,
so `purge_build_cache` emptied the builder cache the default image is
built in. Within a run that costs nothing (the image itself survives),
but the next run's `pinfold build --profile default` starts cold. Measured
on the dev VM at main (12 tests, 6 threads): cold 182.4 s, the next run
177.7 s. `pinfold build --profile default` alone, empty roots: 160.7 s.
The suite's tests after that build all finished within 30 s of it
(par-cold: first test at 158.5 s, last at 182.4 s).

**Change.** Row 15 now has its own cache root and a caller image of its
own, `FROM debian:trixie-slim` alone, set as both projects' `image`. Its
"Shown by" text needs nothing from the default image or the shared
builder. Rows 44 and 50 also build only in their own roots. The default
image is still built once per run, in the suite's cache, by the first
test that asks for it (`default_image`'s `OnceLock`).

**Measurements, dev VM, Linux x64.** "Cold" removes the suite cache
first; "warm" is the next run. The own-cache tests are cold in both.

## Review fixes, round 1

Changes after the first review of PR #381. No binary change.

**Row 50.**
- Tag names carry a random word beside the PID
  (`e2e-<pid>-<word>-<link>`). Before the first build the test fails if
  the store already holds a tag with its prefix; it deletes nothing then.
  The drop guard panics (when the test has not already failed) if the
  image listing is unusable or a delete fails.
- On macOS the root is on the default image, which every other Mac test
  already needs; the test causes no pull of its own. The "Shown by" now
  says so for both platforms.
- The chain is built first; then the cycle is refused as `profile`, and
  once corrected the same spec comes ready.
- The root and the middle link each seed a path of their own, read in the
  box beside the top's replacement seed.
- After the root's recipe change, `pinfold build --profile <root>` builds
  the root alone (the root has no base). A launch then names
  `image-outdated` for the middle and top links and not the root. The
  full rebuild follows, as before.

**Row 44.**
- Both builds run with `--no-cache`; only `--allow` differs.
- The proxied answers are compared by status code (301, 403, 200).
- The egress log is the one new run directory's `egress.jsonl` under the
  state root, not a path parsed from stderr.
- A direct IPv6 attempt to example.com's AAAA address, as the host
  resolves it (`2606:4700:10::ac42:93f3` on the dev VM), fails like the
  IPv4 one: exit 1 with `Network is unreachable`. The dev VM has no IPv6
  route of its own (link-local only), so the v6 attempt has no host-side
  control; the comment says so.

**Row 43.**
- The test fails at the start unless the state root is under `$HOME`,
  telling the runner to set `TMPDIR` under the home and outside any
  checkout.
- The mount check now reads mountinfo's mount root (field 4), not only
  the point. Every mount from under the home is a single file (the disks,
  artifacts, root and init disks and the configuration), never a
  directory, and there is at least one per own disk. The point (field 5)
  is always inside the jail, so the old check was vacuous either way. The
  spec names the kinds of jail entries, not their count: box B, a disk
  project, also has a mount image (`/disk2.ext4`), so an exact count was
  tried and dropped.
- Socket identity no longer comes from `config.json` or from names. The
  vsock directory is the parent of the one socket the VMM listens on, as
  the kernel names it in the VMM's own `/proc/PID/net/unix`. Every socket
  in the jail must be in that directory (by device and inode). Every
  socket file under the state root and `/tmp/pinfold-<uid>` (the spec's
  runtime directory) outside that directory, at least three of them, must
  share no device and inode with anything in the jail.
- The VMM's descriptor table: each descriptor is in the jail, is
  `/dev/null`, or is a socket, pipe or anonymous inode. Observed on the
  dev VM for both VMMs: 0–2 `/dev/null`; `/init.ext4`, `/root.ext4`, each
  `/diskN.ext4`; `/dev/kvm`; one `socket:[…]`; `anon_inode:kvm-vm`,
  `kvm-vcpu:0`–`3`, `[eventpoll]`, `[timerfd]` and `[eventfd]`. Nothing
  outside the jail.

**Harness.** `wait_exited` and `Below::wait_gone` share one rule: a
process has exited when its `/proc/PID/stat` is gone (ENOENT, or ESRCH
while it goes) or it is a zombie; any other read error fails the test.
